# Переход на байтовый контракт Data: чистый кластер, резервное копирование и откат

## Назначение

Документ описывает переход кластера `raftkv` на сборку с байтовым
контрактом `Data` ([API-Data-v3.md](API-Data-v3.md)). Конвертации данных
нет: переход выполняется только на чистом кластере, а возврат — только
восстановлением сохранённой пары «исполняемый файл + резервная копия».

Английская версия — [Data-v3-migration-en.md](Data-v3-migration-en.md).

## 1. Почему нужен чистый кластер

- Сборки до перехода (выпуск на базе `b51e637`) пишут журнал версии 2
  (`logFileVersion = 2` в `pkg/raft/store/log_format.go` этой версии).
  Новая сборка журнал версии 2 не читает: `NewFileStorage` завершает
  процесс с ошибкой `unsupported log version 2`, файл не изменяется,
  автоматической конвертации нет.
- Журналы исследовательской сборки с форматом версии 3 могут содержать
  интерфейсные теги Data 0 и 4. Новая сборка отвергает их как
  повреждение журнала, поэтому гарантировать чтение такого журнала
  целиком нельзя.
- Новое сетевое представление AppendEntries (`AppendEntriesBytesV1`)
  несовместимо с прежним: узел новой сборки закрывает соединение, по
  которому пришёл прежний `AppendEntriesArgs`. Номер `ProtocolVersion`
  остался `3`, согласования версий нет. Поэтому поэтапное обновление по
  одному узлу и смешанный кластер не поддерживаются.
- Снимки прежнего кластера в новые каталоги не переносятся: смешивать
  снимок одного момента с чужим журналом нельзя.

## 2. Порядок перехода

Команды ниже рассчитаны на узлы под Linux: в них используются `/proc`,
`readlink -f` и `findmnt`.

1. Остановить источник нагрузки и убедиться, что он не работает
   (`pgrep -x loadkv` с кодом 1).
2. До остановки узлов на каждом узле записать: PID службы, SHA-256
   реально исполняемого файла (`/proc/<PID>/exe`), его build-info
   (`go version -m`) и копию именно из `/proc/<PID>/exe`, а также версию
   заголовка каждого файла журнала. Версия — байты 8–9 `log.dat`,
   `uint16` big-endian; например,
   `od -An -tx1 -j8 -N2 <каталог>/log.dat` даёт `00 02` или `00 03`.
3. Остановить все узлы. Обновлять только часть узлов нельзя.
4. Проверить реальные пути каталогов данных (`readlink -f`,
   `findmnt -T`); неожиданный путь, символическая ссылка или владелец —
   остановиться.
5. Создать резервную копию данных всех остановленных узлов, конфигурации служб и
   прежних исполняемых файлов на независимый носитель. Проверить SHA-256,
   список и пробную распаковку в пустой каталог. SHA сохранённого
   исполняемого файла должен совпасть с SHA из шага 2, версии заголовков
   журналов — с прочитанными до остановки. Копия на том же носителе, что
   и данные, не считается резервной копией.
6. Очистить только подтверждённые каталоги данных каждого узла, без
   общих шаблонов путей и без `make clean`. Записать список пустых
   каталогов со временем — до первого запуска новой сборки.
7. Установить на все узлы один и тот же исполняемый файл новой сборки и
   сверить его SHA-256 с манифестом сборки.
8. Запустить все узлы. Проверить SHA реально исполняемого файла
   (`/proc/<PID>/exe`), одного лидера, отсутствие ошибок открытия и
   декодирования журнала.
9. В журналах узлов за весь запуск не должно быть строк
   `kvservice: corrupt command` и ошибок загрузки журнала версии 3.

Состояние, накопленное до перехода, в новом кластере отсутствует: оно
остаётся только в резервной копии.

## 3. Откат

1. Остановить источник нагрузки и все узлы новой сборки.
2. Отдельно сохранить и проверить данные и журналы новой сборки.
3. Вернуть исполняемые файлы, SHA которых записан в шаге 2 перехода для
   этой резервной копии, и соответствующие файлы конфигурации служб.
4. Восстановить согласованную резервную копию всех узлов в подтверждённые
   каталоги, проверить SHA и права.
5. Запустить кластер из этой пары «исполняемый файл + резервная копия».

Если SHA исполняемого файла или версии журналов не совпадают с
записанными для резервной копии, откат останавливается до решения владельца
кластера; подбирать другой исполняемый файл нельзя. Новую сборку нельзя
запускать на старых данных, а старую — на данных новой сборки.

**Потеря данных при откате.** Восстановление прежней резервной копии не сохраняет записи,
полученные кластером после перехода. Обратной конвертации журнала новой
сборки нет; данные новой сборки сохраняются отдельно только для разбора.

## 4. Что не поддерживается

- Поэтапное обновление и кластер из узлов разных сборок.
- Чтение журнала версии 2 и журналов с тегами Data 0 или 4.
- Контракт `Apply(any)`: прикладной код, вызывающий `Server.Apply`
  напрямую, передаёт готовые байты (`[]byte`), например результат
  `kvservice.EncodeCommand`.
- Перенос старых снимков в каталоги нового кластера.

Формат снимков KV, их метаданных и постоянных скаляров не менялся
(раздел 7 [API-Data-v3.md](API-Data-v3.md)); это не делает старые
каталоги совместимыми, потому что журнал рядом со снимком другой.

## Синхронизация версий

Русская версия — основная. Английская версия
[Data-v3-migration-en.md](Data-v3-migration-en.md) обновляется в той же
задаче, что и любое изменение фактов русской версии.
